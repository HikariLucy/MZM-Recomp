## Additional executable-RAM findings

### Audio IWRAM copies — normal boot path

`InitializeAudio()` copies three ROM routines into IWRAM and calls them through function pointers:

```text
CallSoundCodeA -> gSoundCodeA
CallSoundCodeB -> gSoundCodeB
CallSoundCodeC -> gSoundCodeC
```

Known ROM source anchors:

```text
CallSoundCodeB = 0x08004310
CallSoundCodeC = 0x080043B4
CallSoundCodeA = 0x08004464
```

These are now represented and code-generated successfully:

```text
gSoundCodeA  0x03003B90 <- CallSoundCodeA 0x08004464  size=0x658  Thumb
gSoundCodeB  0x030041EC <- CallSoundCodeB 0x08004310  size=0x0A4  Thumb
gSoundCodeC  0x03004294 <- CallSoundCodeC 0x080043B4  size=0x0B0  Thumb
```

Together with the IRQ copy:

```text
gInterruptCode 0x03000C7C <- IntrMain 0x08000104 size=0x200 ARM
```

the configured analyzer reports `code_copies=4`, `undefined=0`, and exits successfully. All four RAM destinations are present in the generated symbol map and dispatch table.

### SRAM stack-local executable copies — normal save path

`SramWriteUnchecked()` and `SramCheck()` copy helper routines into local arrays on the guest stack and call those RAM copies through Thumb function pointers.

This is not a fundamental framework blocker: GBARecomp includes hybrid/interpreter/self-healing support for unresolved RAM-installed code. It **is** a strict-static closure item because stack placement is runtime-dependent.

Initial policy:

- allow hybrid execution during M1/M2 discovery;
- capture actual runtime PCs/source mapping;
- convert stable observed placements to reviewed static aliases/source-backed entries where appropriate;
- do not claim strict-static save-path closure until this is resolved.

### Chozodia escape HBlank code — later gameplay

`ChozodiaEscapeHBlank` is copied into a RAM buffer and installed as the HBlank callback during the late-game escape sequence.

This does not block Boot→Title→first-playable-room qualification and is tracked for M4 full compatibility.

## Known framework accuracy caveat: WAITCNT

MZM explicitly writes `WAITCNT` during initialization and SRAM operations.

The pinned framework stores the register and models bus timing, but upstream accuracy documentation still calls out WAITCNT/prefetch timing as an area requiring differential validation. Therefore this is **not** marked fully supported for MZM timing yet.

This is an accuracy/phase risk, not evidence of an inability to execute the game.

## Ownership and acceptance plans for identified gaps

### PPU mosaic

**Ownership:** generic GBARecomp runtime/PPU capability, not MZM-specific game logic.

MZM writes `REG_MOSAIC` during normal gameplay and uses OBJ mosaic on multiple enemies/effects. The pinned GBARecomp accuracy documentation explicitly states that mosaic rendering is not implemented.

**M0 disposition:** ordinary framework gap; does not prevent M1 native bootstrap.

**Acceptance criteria before declaring affected gameplay visually accurate:**

1. implement BG mosaic for supported tile/affine modes used by MZM;
2. implement OBJ mosaic in the sprite compositor;
3. respect horizontal and vertical mosaic sizes from `REG_MOSAIC`;
4. add deterministic PPU tests covering BG and OBJ mosaic;
5. validate at least one MZM scene/effect that actively changes mosaic.

Preferred path: implement generically in GBARecomp and contribute upstream rather than carrying a game-specific renderer hack.

### Mutable same-PC haze code

**Ownership:** generic static-dispatch/code-copy capability in GBARecomp, with MZM configuration supplying the variant inventory.

MZM's `HazeSetupCode()` copies several different Thumb routines into the same `gNonGameplayRam.inGame.hazeCode` buffer and calls the buffer through `gHazeProcessCodePointer`.

Confirmed source variants include:

```text
Haze_Bg3
Haze_Bg3StrongWeak
Haze_Bg3NoneWeak
Haze_Bg3Bg2StrongWeakMedium
Haze_Bg3Bg2Bg1
Haze_PowerBombExpanding
Haze_PowerBombRetracting
```

A fixed runtime-address → single-ROM-source mapping cannot represent all of these variants simultaneously.

**M0 disposition:** bounded strict-static gap, not a native/hybrid execution no-go.

**Bring-up policy:**

- allow hybrid/self-healing execution for an unresolved haze RAM target during M1–M3;
- log copied bytes/source identity and actual runtime dispatches;
- do not hand-edit generated C++;
- prefer a generic GBARecomp solution that can dispatch a fixed RAM PC according to the currently installed source variant.

**Strict-static acceptance criteria:**

1. every observed haze source variant has a reviewed static translation;
2. execution at the shared RAM address selects the currently installed variant without interpreter fallback;
3. qualified haze/power-bomb routes produce zero unexpected dispatch misses;
4. differential/runtime validation confirms the selected variant changes when MZM overwrites the buffer.

### Deferred executable-RAM paths

`ChozodiaEscapeHBlank` is a late-game fixed RAM copy and the bundled NES Metroid has substantially more dynamic executable regions. These are classified as **M4 compatibility work** and do not block M0 exit or M1 bootstrap.
