# M0.6 Evidence — Hardware / Runtime Support Matrix

**Date:** 2026-09-28  
**State:** **EXPERIMENTAL / IN PROGRESS**

## 1. Scope

This gate asks a different question from M0.5:

> Given MZM's actual hardware behavior, can the pinned GBARecomp runtime model the systems needed by the game?

A subsystem marked **SUPPORTED** means an implementation exists in the pinned framework and its shape matches MZM's requirement. It does not replace MZM-specific runtime validation.

Status vocabulary:

- **SUPPORTED** — framework implementation exists and no MZM-specific mismatch is known.
- **SUPPORTED / VALIDATE** — implementation exists, but MZM route/timing behavior must be measured.
- **CONFIG GAP** — framework mechanism exists; MZM metadata is incomplete.
- **ENGINE GAP** — required behavior is not represented sufficiently by the pinned framework.
- **DEFERRED M4** — not needed for boot/initial gameplay proof and intentionally postponed.

## 3. Executable RAM inventory

### 3.1 Confirmed fixed mapping already modeled

```text
IntrMain 0x08000104
    -> gInterruptCode 0x03000C7C
size 0x200
ARM
```

This mapping was emitted successfully into the first MZM dispatch corpus.

### 3.2 Fixed mappings discovered during M0.6

These use stable source→destination relationships and fit GBARecomp's existing `[[code_copy]]` model once exact runtime addresses are pinned:

| Destination | Source | Mode | Size known from source |
|---|---|---|---:|
| `gSoundCodeA` | `CallSoundCodeA` | Thumb | 1624 bytes |
| `gSoundCodeB` | `CallSoundCodeB` | Thumb | 164 bytes |
| `gSoundCodeC` | `CallSoundCodeC` | Thumb | 176 bytes |
| `inGame.clipdataCode` | `ClipdataConvertToCollision` | Thumb | 640 bytes |
| `chozodiaEscape.hblankCode` | `ChozodiaEscapeHBlank` | Thumb | code copy requests 0x20 halfwords = 0x40 bytes |

The decomp documents a game bug in the clipdata case: the copied function's switch table can jump back into ROM. That is still compatible with a RAM entry mapping, but it requires runtime validation.

### 3.3 Mutable same-PC mapping — haze

MZM's `HazeSetupCode()` copies different source functions into one shared 512-byte destination:

```text
gNonGameplayRam.inGame.hazeCode
```

Known source variants include:

- `Haze_Bg3`
- `Haze_Bg3StrongWeak`
- `Haze_Bg3NoneWeak`
- `Haze_Bg3Bg2StrongWeakMedium`
- `Haze_Bg3Bg2Bg1`
- `Haze_PowerBombExpanding`
- `Haze_PowerBombRetracting`

The runtime pointer always calls the same RAM buffer address (Thumb bit set), but the bytes occupying that address change according to the active haze mode.

The pinned GBARecomp static mapping is fundamentally a fixed:

```text
runtime address range -> one immutable ROM source range
```

and its dispatch identity is keyed by guest address/mode. Multiple `[[code_copy]]` declarations for the same runtime PC cannot represent simultaneous alternative native bodies: the first matching fixed mapping determines the ROM source used for discovery.

**Classification: ENGINE GAP for strict-static full gameplay.**

This does not block:

- M1 static bootstrap;
- boot / intro / title work;
- initial gameplay bring-up if the qualified route does not execute a haze variant.

It does block a truthful claim of full strict-static MZM compatibility until a variant-aware solution exists.

## 4. PPU mosaic gap

MZM actively writes `REG_MOSAIC` and uses mosaic-related object/gameplay state. The pinned GBARecomp PPU implements the tile/affine modes, OBJ, windows and blending needed by MZM, but does not currently apply the MOSAIC effect during rendering.

**Classification: ENGINE GAP for visual parity.**

Expected ownership: generic GBARecomp PPU improvement, preferably contributed upstream rather than implemented as an MZM-only rendering hack.

This gap affects presentation correctness, not CPU execution reachability.

## 5. Known framework limitations that are not current blockers

### Bitmap modes 3/4/5

The pinned PPU does not render bitmap modes 3/4/5. The MZM source audit found no normal Zero Mission use of those modes; explicit mode use found in normal source is mode 1, while most screens use mode 0 defaults.

Therefore bitmap rendering is not currently an MZM M0 blocker.

### DMA3 video capture

Not modeled by the pinned DMA runtime. No normal MZM requirement has been identified.

### General mid-scanline MMIO

The renderer is scanline-oriented rather than a general per-pixel MMIO renderer. MZM's known HBlank effects happen on HBlank boundaries, for which the framework has HBlank events/IRQs and timed DMA. Validate visually rather than assuming equivalence.

## 6. Ownership plan

| Gap / work item | Owner target | Gate |
|---|---|---|
| Fixed MZM code-copy metadata | MZM-Recomp | all known fixed RAM execution roots represented |
| Mutable haze code variants | GBARecomp engine first; MZM config only describes variants | same RAM PC executes correct native body after every supported copy transition |
| MOSAIC rendering | GBARecomp PPU upstream | deterministic MZM mosaic scene matches a trusted GBA reference |
| MZM HALT/IRQ/DMA timing | MZM-Recomp validation | boot/title route shows no unexpected IO/IRQ/timing failures |
| MZM audio | MZM-Recomp validation; generic bugs upstream | correct FIFO/timer/DMA behavior on deterministic route |
| Fusion link | M4 | validate cable/SIO + Timer3 route |
| NES Metroid | dedicated M4 workstream | separately qualified dynamic-code architecture |

## 7. Current verdict

No hardware gap found so far invalidates the project architecture or blocks **M1 static bootstrap**.

M0.6 is not yet closed because:

1. exact addresses for the newly identified fixed executable RAM copies still need to be captured from the matching ELF;
2. the mutable-haze and mosaic gaps need explicit implementation milestones in the project roadmap.

Current project verdict remains:

**GO WITH CONDITIONS.**
